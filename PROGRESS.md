## Что не проверено и чего нет

- **CI** (GitHub Actions, Ubuntu, Python 3.12): первый прогон зелёный: `make lint`, `make test` (включая CI-гейт на фикстурах с реальными моделями), `make fetch`, `make eval` (оба датасета, кассеты `cassettes/eval`). Холодный прогон занял около 28 минут, почти всё это cross-encoder на CPU раннера; кэш `.cache` сохраняется для следующих запусков. Этим же проверены цели Makefile `lint test fetch eval`.
- Цели Makefile `up`, `index` (нужен Docker/Qdrant), `tune`, `record` (нужен Ollama) и `demo` через `make` не запускались; `tune`, `record` и демо-команда CLI прогонялись напрямую через `uv run`.
- **Живая латентность и стоимость LLM**: цены в конфиге нулевые по решению владельца (локальная модель), латентность по кассетам не измеряется.
- Кассеты фикстур `tests/cassettes/` записаны эвристическим двойником `fake-heuristic-v1`, это не модель. CI-гейт защищает пайплайн от регрессий, но не говорит о качестве LLM. Реальные кассеты (`cassettes/eval/`, `qwen2.5:14b`) покрывают только test-сплит Abt-Buy.
- `make demo` (`uv run python -m entity_cascade.cli match --demo 100 --llm recorded`): первые 100 строк test; кассеты есть только для строк, попавших в серую зону test, поэтому для этих строк LLM-этап работает, а промах кассеты отключает его с пояснением.

## Этап 1. Каркас

`pyproject.toml` (uv, Python 3.12, CPU-индекс torch для Linux), `docker-compose.yml` (Qdrant), `Makefile` (`up down test lint fetch index eval record demo`), `.github/workflows/ci.yml`, `configs/default.yaml`, типизированный конфиг на Pydantic v2 (`extra="forbid"`).

## Этап 2. Загрузка и нормализация

- `scripts/fetch_data.py`: скачивает архив с `dbs.uni-leipzig.de`, проверяет sha256. Эталонный хеш заранее не был известен (выдумывать его нельзя), поэтому при первом скачивании он записывается в `data/checksums.json` (trust on first use), дальше проверка строгая. Записаны хеши `abt_buy` и `amazon_google`.
- Кодировка: `Abt.csv` не читается как utf-8 (байт 0xAE), остальные файлы читаются. `read_text_auto` пробует utf-8, cp1252, latin-1.
- Нормализация, токенизация для BM25, извлечение артикулов, бренд из словаря каталога. Сплит строк Abt 50/50 по seed.
- Фикстуры `tests/fixtures/`: 50 строк Abt, 241 товар Buy, 51 пара.

Реальная статистика Abt-Buy (`dataset_stats`): 1081 строка Abt, 1092 товара Buy, 1097 пар; у **всех** строк Abt есть пара; 16 строк с несколькими парами; общий артикул у 773 из 1097 пар. Отсюда отклонение от плана:

- **Синтетические «новые товары».** Без них зону `no_match` не оценить. В `default.yaml` `new_product_fraction: 0.15`: у 15% строк каждого сплита истинные товары удаляются из каталога (только те, что не нужны другим строкам). Везде помечено как синтетика. Это решение принято без ответа владельца (вопрос был в PLAN.md).

## Этап 3. Кандидаты

BM25 (`rank_bm25`), dense (`bge-small` в Qdrant; в тестах и eval `:memory:`), RRF k=60, top-20. Отчёт показывает recall@1/@5/@20 по каждому режиму; на Abt-Buy recall@20 гибрида близок к 100%, но каталог маленький (раздел 2 DESIGN.md).

## Этап 4. Reranker

Cross-encoder (логиты, не сигмоида) + пять признаков артикула/бренда, веса перебором по сетке на val. Находки, которые вошли в DESIGN.md:

- reranker сам по себе не лучше порядка RRF по top-1; основной выигрыш дают признаки;
- вход cross-encoder выбран на val скриптом `scripts/ce_input_experiment.py`: запрос из названия лучше, чем название с описанием (`rerank.query_fields` по умолчанию `["name"]`);
- кэш скоров на диске (`.cache/rerank_scores.jsonl`, ключ — sha256 от модели и пары) ускоряет eval с ~10 минут до ~2; латентность меряется отдельно, без кэша, на 50 строках val.

## Этап 5. Пороги и зоны

- `calibration.py`, `zones/thresholds.py`: auto_match = score ≥ high и margin ≥ margin_min (самая большая зона с precision ≥ цели на val); llm_arbiter = не auto и score ≥ low; no_match = не auto и score < floor; human_review = остальное. Отклонение от формулировки ТЗ: появился третий порог `floor` для `no_match`, потому что «два порога» не позволяют отделить «совсем далеко» от «человеку».
- Защита от утечки: `ValSplit` и `TestSplit` — разные типы; `tests/test_no_leakage.py` (заминированные метки test, перемешанные и обнулённые метки test дают побитово тот же результат, метки val меняют результат, AST-проверка модулей подбора).
- Итог на Abt-Buy (см. `reports/results.md`): auto-зона на val достигает цели по построению, на test precision ниже; `no_match` на val недостижима (строки без пары по score плохо отделяются), поэтому она пуста, а серая зона содержит около 41% строк без пары; `human_review` практически пуста (нижняя граница арбитра не ограничивает).
- Параметр `llm_min_answerable` (по умолчанию 0.5): строка «отвечаема», если истинный товар среди показанных кандидатов или пары нет вовсе. Сначала критерий считал только «есть среди показанных», это занижало долю отвечаемых; исправлено до просмотра test-метрик арбитра.

## Этап 6. LLM-арбитр

`LLMClient` (async), `FakeLLM`/`HeuristicFakeLLM`, `RecordedLLM` (sha256 от модели и промпта, промах кассеты — исключение), `RecordingLLM` (`make record`), `OpenAICompatibleLLM` (семафор на уровне арбитра, таймаут, ретраи с backoff и jitter на 408/409/425/429/5xx и транспортные ошибки, `Retry-After`). Промпт с позицией и top-3, JSON `{choice, confidence, reason}` через Pydantic; невалидный ответ и ошибка провайдера уводят строку к человеку. Метрики: сколько строк снято с человека, точность (отдельно «этот товар» и «none»), токены, стоимость на 1000 строк по ценам из конфига (цены по умолчанию 0, это явно пишется в отчёте).

## Этап 7. Отчёт и Amazon-Google

- `make eval` пишет `reports/results.md`, `results.json`, `calibration.json`, три PNG и блок цифр в README (между маркерами).
- Сравнение режимов «на равных» (каждый режим доверяет своему score и margin), кривая автоматизация↔precision, таблица компромисса (цель precision 90–99.5% и нижняя граница Уилсона), латентность.
- Amazon-Google (`configs/amazon_google.yaml`, Amazon — прайс, Google Products — каталог, 250 строк без пары естественным образом): пороги с Abt-Buy без пересчёта дают auto-зону с заметно более низкой precision, чем цель, а при пересчёте на собственном val цель недостижима, auto-зона пуста. Пороги не переносятся; причина не исследовалась (общий артикул есть у 55 из 1300 пар).
- CI-гейт: `eval_thresholds.yaml` + `tests/test_gate.py` (реальные модели на фикстурах, кассеты `tests/cassettes`). Пороги гейта поставлены ниже измеренных значений: на фикстуре в test всего 25 строк, одна строка — 4 пункта.
- Найденный и исправленный дефект: `results.json` не читался обратно (NaN писался как null); добавлен тип `NanFloat` и тест на round-trip.

## Этап 8. CLI

Нужен `reports/calibration.json`. `--llm none|fake|recorded|openai`, по умолчанию `none`: серая зона уходит человеку.

## Запись кассет (Ollama, qwen2.5:14b)

Выбрана `qwen2.5:14b` (уже была установлена; `qwen2.5:7b-instruct` владелец качать не стал). Конфиг: `base_url: http://localhost:11434/v1`, цены 0, `max_concurrency: 2`, `timeout_s: 180`. `make record` сначала проверяет сервер и наличие модели; есть `record --dry-run`. Записано 174 из 174 ответов в `cassettes/eval/` (серая зона test на Abt-Buy), ошибок провайдера и формата нет.

Первый (неоптимизированный) прогон, промпт v1: арбитр решил 100% серой зоны test с точностью ответов 64.9%; ответы «none» были неточны (54.3%), recall системы упал до 86.3% против 99.1% без LLM; confidence ничего не фильтровал.

### Тюнинг на val (`make tune`)

Правило выбора зафиксировано в конфиге и в коде (`eval/llm_tuning.py`) **до** первых вызовов на val: самый широкий набор строк, решаемых с точностью не ниже `llm.target_accuracy` (0.90) на val, не менее 10 решённых строк; сетка порога 0.5–0.95; версии промпта v1–v4 (v1 — черновик без изменений, v2 — явная процедура по номеру модели, v3 — v2 с «сначала сравни», v4 — v3 с подсказками правил). На val записано 188 × 4 ответов. Выбрано: **v2, `min_confidence` 0.6** (на val 90.3% точности на 72 решённых строках, цель достигнута, но на границе). Test в подборе не участвовал; его v1-кассеты (первый прогон) я до этого видел, они не влияли на выбор, который сделан по val-таблице.

Модуль подбора принимает только val-данные (тест на сигнатуру и AST-проверка исходника, `tests/test_llm_tuning.py`).

### Итог на test с выбранным промптом

Записано 174 из 174 ответов (`make record`, средняя живая латентность около 1.2 с на вызов). В отчёте: арбитр снимает с человека около 45% серой зоны с точностью решённых ответов 84.8% (на val было 90.3%: та же усадка, что у порогов), система с LLM автоматизирует 82.3% строк, 17.7% остаётся человеку; precision 96.3% и recall 97.2% против 97.4% и 99.1% у каскада без LLM. Цены нулевые (локальная модель).

Кассеты в `cassettes/eval/`: v1-test (174), val для v1–v4 (752), v2-test (174). Кассеты Amazon-Google не записывались.
