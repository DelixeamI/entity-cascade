Сопоставление строк прайса поставщика с каталогом товаров каскадом: дешёвый поиск, reranker (cross-encoder), LLM для спорных строк и человек для неуверенных.
Главная тема проекта: компромисс, который неизбежен в такой системе, между долей автоматизации и точностью автоматических ответов. Он измеряется на отложенной (test) выборке.

```mermaid
flowchart LR
    row["строка прайса"] --> ret["BM25 + dense (Qdrant)<br/>слияние RRF, top-20"]
    ret --> rr["cross-encoder + признаки артикула и бренда<br/>score и margin"]
    rr -->|"score и margin высокие"| auto[auto_match]
    rr -->|"серая зона"| llm["llm_arbiter<br/>top-3 кандидата, ответ в JSON"]
    rr -->|"между порогами"| human[human_review]
    rr -->|"score слишком низкий"| none[no_match]
    llm -->|"уверен"| done["ответ дал LLM"]
    llm -->|"не уверен, невалидный ответ или ошибка провайдера"| human
```

## Запуск за минуту

Нужны Python 3.12 и [uv](https://docs.astral.sh/uv/). API-ключи и GPU не нужны: модель эмбеддингов (`BAAI/bge-small-en-v1.5`) и reranker (`cross-encoder/ms-marco-MiniLM-L-6-v2`) небольшие и работают на CPU; при первом запуске они скачиваются с Hugging Face Hub.

```bash
uv sync
make fetch      # скачивает Abt-Buy и проверяет sha256
make eval       # reports/results.md, reports/*.png, блок с числами выше
make demo       # 100 строк через CLI -> out/demo_result.csv
make test       # юнит-тесты + CI-гейт на срезе фикстур
make tune       # нужна Ollama: подбор промпта и порога LLM на val
make record     # нужна Ollama: запись ответов на test-выборке
```

В Windows без `make` выполняйте команды из `Makefile` через `uv run ...`.

Сопоставить собственный прайс (колонки `id`, `name`, при желании `description`):

```bash
uv run python -m entity_cascade.cli match --input price.csv --output result.csv
```

В результате для каждой строки записаны зона, вердикт (`match`, `no_match`, `needs_human`), кто принял решение, найденный товар каталога, score, margin и текстовая причина; в конце печатается сводка. CLI требует `reports/calibration.json`, который создаёт `make eval`.

## LLM: что записано, а что нет

Арбитр работает через интерфейс `LLMClient` с тремя реализациями:

- `FakeLLM` / `HeuristicFakeLLM`: тестовые двойники. Это не модели, и их точность нигде не выдаётся за качество LLM.
- `RecordedLLM`: воспроизводит кассеты (`tests/cassettes/`, `cassettes/eval/`) по ключу sha256 от модели и промпта. Отсутствующая кассета даёт ошибку, а не выдуманный ответ. Благодаря этому `make test` и `make eval` работают без API-ключей.
- `OpenAICompatibleLLM`: любой OpenAI-совместимый endpoint `/chat/completions` (Ollama, vLLM, облачный API) через `llm.base_url`, `llm.model` и ключ в `$LLM_API_KEY`. Параллелизм ограничен семафором, на 429 и 5xx выполняются повторы с экспоненциальным backoff и jitter, у каждого запроса есть таймаут.

`make tune` записывает ответы арбитра на серой зоне val для каждой версии промпта и выбирает версию и `llm.min_confidence` по правилу из конфига (только по val). Затем `make record` прогоняет выбранный промпт на test и пишет кассеты. Смена промпта, модели или порогов (они определяют, какие строки попадают к арбитру) требует перезаписи кассет.

## Данные

Abt-Buy и Amazon-Google взяты из коллекции бенчмарков Лейпцигского университета по entity resolution (<https://dbs.uni-leipzig.de/research/projects/benchmark-datasets-for-entity-resolution>). `make fetch` скачивает их и проверяет sha256 из `data/checksums.json` (хеш фиксируется при первом скачивании, доверие при первом использовании). В самом репозитории лежат только срез из 50 строк в `tests/fixtures/` и промпты с ответами LLM для строк серой зоны в `cassettes/`: в них цитируется текст товаров из датасета. Перед распространением проверьте условия использования бенчмарка.

## Ограничения

- Кассеты фикстур в `tests/cassettes/` записаны эвристическим тестовым двойником. Поэтому CI-гейт защищает пайплайн от регрессий, но ничего не говорит о качестве LLM. Реальная запись (`cassettes/eval/`, `qwen2.5:14b` через Ollama) покрывает только серые зоны val и test на Abt-Buy; версия промпта и `min_confidence` выбраны на val (`make tune`), падение точности арбитра с val на test показано в отчёте.
- Abt-Buy мал, а его каталог состоит ровно из товаров, у которых есть пары. На реальном каталоге в сотни тысяч позиций recall поиска будет ниже; мерить нужно в первую очередь его.
- У каждой строки Abt есть истинная пара, поэтому зону `no_match` на сырых данных оценить нельзя. Конфиг по умолчанию удаляет из каталога истинные товары случайной доли строк («синтетические новые товары»); везде, где это влияет на число, это помечено.
- Пороги подобраны на половине небольшого датасета. Разрыв между precision auto-зоны на val и на test показан, а не скрыт; см. таблицу компромисса.
- Пороги привязаны к домену: раздел про второй датасет показывает, что происходит без перекалибровки.
- Настройки арбитра подобраны на 188 строках серой зоны val и для одной модели. Для другой модели нужен свой `make tune`; самоотчётный confidence служит лишь грубым фильтром, и его смысл зависит от промпта.
- Латентность это замеры одного процесса на CPU той машины, где выполнялся `make eval`.
