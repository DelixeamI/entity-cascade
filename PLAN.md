## 2. Метрики и определения (зафиксировать до кода)

- **candidate recall@k**: доля строк с парой, у которых хотя бы один истинный товар в top-k кандидатов.
- **Зоны**: `auto_match`, `llm_arbiter`, `human_review`, `no_match`.
- **precision auto_match** = верные top-1 в зоне / строки в зоне.
- **Доля автоматизации** = (auto_match + решённые арбитром) / все строки. Решённые арбитром — те, где арбитр выдал выбор с confidence не ниже порога из конфига; остальные уходят человеку.
- **Итоговая precision/recall системы при «человек всегда прав»**: строки в `human_review` считаются решёнными верно (и для найденных пар, и для отсутствия пары). Precision и recall считаются по парам, выданным системой без участия человека, плюс отдельно показывается нагрузка на человека (доля строк). Точные формулы напишу в `eval/metrics.py` и продублирую в DESIGN.md, чтобы их можно было проверить.
- **Сплит**: строки Abt делятся 50/50 по seed. Каталог Buy общий (в него идёт поиск). Модели не дообучаются, поэтому утечки через веса нет; подбирается только пороги.

## 3. Защита от утечки test (требование 7)

- `fit_thresholds()` принимает только объект `ValSplit`; тип `TestSplit` отдельный, и функция его не принимает (проверка типов + рантайм).
- Тест 1: обёртка над test-метками, которая бросает исключение при любом чтении во время подбора порогов.
- Тест 2: перемешиваем метки test, подбираем пороги заново — пороги должны совпасть побитово.
- Тест 3: множества id val и test не пересекаются, объединение равно всем Abt id, результат детерминирован при том же seed.
- Метрики на test считаются отдельной функцией и не вызываются из кода подбора.

## 4. Этапы

Каждый этап заканчивается так: `make test` и `make lint` зелёные → обновлён PROGRESS.md → я предлагаю сообщение коммита → остановка до вашего «ок».

### Этап 1. Каркас
Работы: структура, `pyproject.toml` (Python 3.12, uv), `docker-compose.yml` (Qdrant), Makefile (`up`, `test`, `lint`, `fetch`, `index`, `eval`, `record`, `demo`; нереализованные цели печатают понятную заглушку), `ci.yml` (uv, ruff, mypy, pytest, `actions/cache` для uv и каталога моделей HF), `git init`, `.gitignore` (данные и модели не в git).
Критерий: CI зелёный. Я не могу запустить GitHub Actions отсюда; локально проверю тем же набором команд, а статус CI подтвердите вы после пуша. Если репозитория на GitHub ещё нет, так и скажу, а не буду утверждать «CI зелёный».

### Этап 2. Загрузка и нормализация
Работы: `fetch_data.py` (скачивание архива Leipzig, проверка sha256, чтение latin-1/utf-8 с проверкой, а не слепым декодированием), `loader.py`, `normalize.py` (регистр, unicode NFKC, единицы: `GB/gb/Gb`, дюймы, `"`, разделители), извлечение артикулов/моделей регулярками, `split.py`, фикстуры: 50 строк Abt + их кандидаты из Buy.
Про sha256: эталонный хеш пока неизвестен, я не буду его придумывать. Первое скачивание считает хеш, я записываю его в `data/checksums.json`, дальше проверка идёт по нему (доверие при первом скачивании, это отмечу в DESIGN.md). Лицензию набора и допустимость фикстур в git проверю и отмечу в README.
Тесты: нормализация (таблица вход → выход), артикулы, кодировка, сплит и детерминизм.
Критерий: реальная статистика датасета (число строк, пар, строк с несколькими парами, строк без пары) записана в PROGRESS.md.

### Этап 3. Кандидаты
Работы: BM25 (`rank_bm25`), dense (bge-small, Qdrant; в тестах `:memory:`), RRF, top-20. Eval: candidate recall@1/@5/@20 для bm25 / dense / hybrid.
Критерий: цифры выводит `make eval` в `reports/results.md`. Если recall@20 низкий, это прямо записывается в DESIGN.md: дальше каскад ничего не исправит, потолок задаёт этап поиска.
Деталь: для bge-small используется query-инструкция в запросе; проверю по карточке модели и запишу, что именно применено.

### Этап 4. Reranker
Работы: cross-encoder по top-20, score и margin (top-1 минус top-2), признаки: совпадение артикула, совпадение бренда. Eval: top-1 accuracy для hybrid и hybrid+rerank на val.
Критерий: цифры в отчёте; тесты на признаки на синтетических примерах и на фикстурах.
Риск: ms-marco-MiniLM обучен на веб-запросах, а не на товарных парах; возможно, он не превзойдёт hybrid. Если так, это будет записано как есть.

### Этап 5. Пороги и зоны
Работы: подбор на val по сетке `(high, margin_min)`: максимальная доля auto_match при precision ≥ целевой (конфиг, по умолчанию 0.98). Порог `low` для `no_match`: наибольший `low`, при котором доля строк с истинной парой, попавших в `no_match`, не превышает `no_match_max_miss_rate` (параметр конфига, значение по умолчанию задам на этом этапе и обосную). Оценка на test: доли зон, precision auto_match, итоговая precision/recall.
Статистика: val около половины Abt, и precision ≥ 0.98 на малой выборке шумная; рядом с точечной оценкой выводится интервал Уилсона, а подбор требует минимальной поддержки зоны (параметр конфига). Если целевая precision не достигается ни при каких порогах, это сообщается, а не замалчивается.
Критерий: тесты утечки из раздела 3 зелёные.

### Этап 6. LLM-арбитр
Работы: `LLMClient` (async), `FakeLLM`, `RecordedLLM` (ключ sha256 от модели+промпта; промах кассеты — явная ошибка, а не тихий ответ), `OpenAICompatibleLLM` (семафор, таймаут, ретраи с backoff и jitter на 429/5xx, лимит попыток), промпт с позицией и top-3 кандидатами, ответ Pydantic `{choice: index | none, confidence, reason}`, обработка невалидного JSON (одна повторная попытка, затем строка уходит человеку). `make record` перезаписывает кассеты; в кассеты пишется usage токенов для расчёта стоимости.
Метрики: сколько строк серой зоны арбитр снял с человека и с какой precision; стоимость на 1000 строк = токены из кассет × цены из конфига.
Ограничение: без реального провайдера я могу проверить только код на FakeLLM и тестовых кассетах. Цифры качества LLM появятся только после `make record` на реальной модели; до этого в отчёте стоит пометка «не записано», а не выдуманное число.

### Этап 7. Отчёт и второй датасет
Работы: `report.py` генерирует `reports/results.md` и PNG: кривая «доля автоматически решённых ↔ precision» по сетке порогов (отдельно val и test), таблица зон, сравнение режимов (bm25 / dense / hybrid / hybrid+rerank / +LLM), латентность (p50/p95 по этапам, замеры на CPU этой машины) и стоимость. Amazon-Google через `amazon_google.yaml`: пороги с Abt-Buy применяются как есть и после перекалибровки на val Amazon-Google; результат записывается честно, даже если пороги окажутся переносимыми. CI-гейт: тест на фикстурах с `RecordedLLM`, пороги из `eval_thresholds.yaml`.
Риск: Amazon-Google заметно сложнее (грязные описания, пары неравномерны), recall@20 может быть низким; тогда это главный вывод для DESIGN.md.

### Этап 8. CLI
`match --input price.csv --output result.csv`: пакетная обработка, колонки результата — зона, кандидат, скор, margin, причина; сводка в stdout (доли зон, время, оценка стоимости). `make demo` — 100 строк. Тесты: CLI на фикстурах, формат CSV, поведение при пустом входе и при отсутствующих колонках.

### Этап 9. Документация
README (две строки сути, mermaid-схема, кривая и таблица из `reports/`, запуск за минуту, ограничения), DESIGN.md (6–8 решений в формате Проблема / Решение / Отвергнутая альтернатива / Цена), QUESTIONS.md (10 вопросов). Все числа в README берутся из сгенерированных отчётов; ручных цифр не будет. Проверю скриптом, что числа в README совпадают с `reports/results.md`.

## 5. Риски и как с ними обращаемся

1. **Низкий recall@20** — потолок системы; фиксируем в DESIGN.md.
2. **Скачивание данных**: сайт Leipzig может быть недоступен или URL изменился — проверю на этапе 2; запасной вариант — попросить вас положить архив вручную.
3. **Размер моделей в CI**: два небольших HF-модели кэшируются, но первый прогон скачивает их из HF Hub (нужна сеть, ключи не нужны).
4. **Недетерминизм**: scores reranker на разных CPU могут отличаться в последних знаках; гейт использует допуски, а не точное равенство.
5. **Кассеты привязаны к промптам**: смена промпта, модели или порогов (меняют состав серой зоны) требует `make record`. Это будет написано в README.
6. **Маленький val**: широкие интервалы; показываем их, не прячем.
